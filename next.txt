Now I understand the workflow you want for TXMate. The important distinction is that TXMate is a peer tutoring platform, not a social network or a general messaging application. Profiles help students choose an Academic Mate, requests establish the relationship, bookings create sessions, and messaging and attendance are tied to those sessions.

I would implement your workflow as follows, using the existing database models and pages wherever possible.

## 1. The complete TXMate workflow

1. Discover an Academic Mate

   Students browse Academic Mates on the Find Academic Mate page or open an individual profile. Both places have a request button.
2. Review the profile and verification status

   Show verified Academic Mates in the discovery results. Clearly distinguish Academic Mate verification from course verification. A verified Academic Mate can offer a course that is still awaiting verification, provided the offering otherwise meets the platform's eligibility rules.
3. Send and respond to a request

   The student submits a request. The Academic Mate reviews it on the Incoming Requests page and accepts or declines it. The student sees the updated status.
4. Book an available session

   After acceptance, the student chooses an available time for the specific course offering. TXMate validates the slot and prevents double-booking.
5. Open the session conversation

   Booking creates a private conversation associated with that session. The Academic Mate controls whether messaging is open or closed. When closed, the student cannot send messages.
6. Collect attendance confirmations

   TXMate prompts the student 10 minutes after the session begins. The Academic Mate receives an attendance prompt 10 minutes before the session ends.
7. Resolve attendance and request a review

   Both participants must agree on attendance before it becomes official. Once attendance is confirmed, the student can review the Academic Mate.

## 2. The timing rules

For your example of a session running from 3:00 p.m. to 4:00 p.m.:

## 2:50 PM

Student reminder

The session is about to begin in 10 minutes.

## 3:10 PM

Student attendance prompt

The student indicates whether they attended. This is a preliminary response, not yet official attendance.

## 3:50 PM

Academic Mate attendance prompt

The Academic Mate confirms or disputes the student's response.

Attendance agreement

Once both responses agree, TXMate records the official outcome and enables the review process.

### Handling disagreements

Suppose the student says they attended, but the Academic Mate says they did not.

- TXMate asks the Academic Mate to confirm that response.
- If the Academic Mate confirms again, the system records the disagreement rather than treating the student's response as official attendance.
- The session must not receive an official attendance record until the conflict is resolved. If the student disputes the decision, the system should retain the case for resolution rather than silently deleting evidence.

This preserves your rule that conflicting responses cannot count as verified attendance while avoiding the loss of records needed to resolve disputes.

## 3. How messaging should work

The conversation should be associated with a specific booking, not merely with two users.

| Action                          | Expected behaviour                                                                            |
| ------------------------------- | --------------------------------------------------------------------------------------------- |
| Session booked                  | A conversation becomes available for that session.                                            |
| Academic Mate opens messaging   | Both participants can exchange messages.                                                      |
| Academic Mate closes messaging  | The student can read the history but cannot send messages.                                    |
| Academic Mate reopens messaging | Both can continue the same conversation.                                                      |
| Session ends                    | The conversation remains tied to the session, with messaging controlled by the Academic Mate. |

I recommend retaining the conversation history rather than deleting it when messaging closes. Closing should change permission to send, not erase previous arrangements.

## 4. How this fits the existing codebase

The repository already contains `MateRequest`, `TutoringSession`, `Conversation`, `Message`, `Attendance`, `Review`, and `Notification` models. We should extend these existing structures where necessary instead of creating a parallel system.

The main implementation work is:

1. Public Academic Mate profile viewing and request buttons.
2. Transparent Academic Mate and course verification labels.
3. Booking against actual availability, with conflict prevention.
4. Session-specific messaging with Academic Mate-controlled access.
5. Scheduled reminders and attendance prompts.
6. Mutual attendance confirmation, dispute handling, and review eligibility.

One technical detail matters: the reminders must be generated by server-side scheduling or another reliable background mechanism, not just by a timer running in the student's browser.

My recommendation is to start with profile viewing and request integration, because that is the current stage of TXMate and the entry point to the entire workflow. We should complete that stage against the existing routes and UI before moving on to booking.
